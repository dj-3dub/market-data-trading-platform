# SRE scenario: Kafka dependency failure

## Objective

Show how the trading data lab **detects, contains, and recovers from a Kafka
dependency failure**, with evidence rather than assumptions. This is not a
high-availability Kafka cluster: Compose runs one broker and one ZooKeeper.
The drill **intentionally restores the broker** after a pause. It tests client
reconnection and data integrity; it does not prove broker auto-failover.

## Safety and prerequisites

Use a **disposable local development stack only**. The experiment pauses the
Kafka service and disrupts processing. Do not use this against real trading
systems, shared environments, or valuable data. Keep all Compose volumes
intact; do not use `make clean`.

Start the project and wait for fresh data:

```bash
PROMETHEUS_PORT=9091 make up
PROMETHEUS_PORT=9091 python3 scripts/verify-pipeline.py
```

Set `PROMETHEUS_PORT` consistently with the running stack (9090 otherwise).

## Run the end-to-end drill

```bash
SRE_DRILL_ACK=local-lab PROMETHEUS_PORT=9091 make sre-kafka-drill
```

The runner performs the following gates in order:

1. Verify a healthy live pipeline before fault injection.
2. Run the **existing** `failure-suite.py broker` scenario. It pauses Kafka,
   waits for a degraded readiness response **and** a firing alert, restores the
   broker, then requires clear alerts and three advancing, fresh samples.
3. Verify the live pipeline again.
4. Run the existing persistence verification (Kafka record, consumer offsets,
   Grafana dashboard, and Prometheus history).

A failing gate stops the run. The fault suite attempts broker restoration in
a `finally` block, but an interrupted shell or host crash may still require
`docker compose unpause kafka`. **Check broker state after an interrupted drill.**

## Artifacts and interpretation

- `artifacts/sre-kafka-drill.json`: ordered gates and pass/fail outcome.
- Existing `artifacts/fault-broker*.json`: fault timing and observations
  as generated by `scripts/failure-suite.py`.
- Existing pipeline and persistence evidence: generated by the respective
  validation scripts.

**Success** means the current harness observed an outage signal, restored the
paused dependency, recovered fresh data flow, and passed the follow-up
integrity checks. It does **not** prove zero lost ticks, multi-broker high
availability, a particular SLO, or automatic infrastructure repair.

## Interview discussion

> When Kafka stops accepting traffic, producers retain unacknowledged events in
> a local SQLite outbox for retry. The strategy uses a local transactional
> checkpoint and event deduplication; stale data does not generate BUY signals.
> In this single-broker lab, we restore Kafka and verify fresh processing,
> alert clearance, and post-recovery persistence. Broker failover remains a
> separate engineering milestone.

Ground that answer in the generated reports, not merely the design. Investigate
failures using `docker compose logs kafka market-data strategy-engine`,
`/ready`, Prometheus alerts, and Kafka consumer lag.

## Next steps

- Add an automatic, crash-safe fault restoration supervisor external to the
  experiment and measure recovery after a real broker process restart.
- Prove source-sequence continuity and zero unintended BUY effects **across**
  broker failure with explicit before/after identity comparisons.
- Test DNS errors, network partitions and prolonged broker unavailability.
- Add OpenTelemetry traces correlating API requests with downstream work.
- Introduce multi-broker Kafka and replication only after this single-broker
  recovery baseline is repeatable.
